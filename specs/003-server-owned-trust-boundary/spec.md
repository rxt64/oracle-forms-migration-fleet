# 003 — Server-owned trust boundary for the workbench API

## How this document was produced

Spec Kit is not installed in this repository and no `.specify/` tooling is present, so this folder was
written by hand in the shape the existing `specs/001-*` and `specs/002-*` folders use. Nothing here was
generated by `specify`, and the numbering is a convention followed manually.

## Problem

`MigrationRunRequest` carries three kinds of claim that are authority rather than data:

| Claim | Field | What accepting it from a caller means |
|---|---|---|
| This artifact is verified | `EvidenceItem.IsVerified`, `EvidenceItem.Signals` | A browser decides what the planner treats as established fact |
| A human approved this gate | `HumanApproval.Decision`, `HumanApproval.ApproverId` | A browser opens the sandbox and production gates by naming an approver |
| This phase completed | `MigrationAttestation` | A browser signs off work no adapter performed |

Both `POST /api/workbench/plan` and `POST /api/workbench/execute` deserialized these straight from the
request body. A caller could therefore post `isVerified: true` on every evidence kind, `Approved` on all
three approvals, and the three attestations production cutover requires, and the deterministic planner —
working correctly, from the inputs it was given — would authorize `ProductionCutover`.

The gates were never weak. The inputs to them were caller-controlled, which is the same outcome by a
different route.

## Non-goals

- Building an authorization issuing service. There is no trusted identity and persistence tier behind
  this workbench yet, and inventing one in the request path would be the defect this spec exists to fix.
- Changing what the planner decides from a given set of facts. `MigrationRunPlanner` is untouched.
- Changing the source acquisition, artifact preview, or export contracts.

## Requirements

### R1 — Untrusted at both boundaries

`IsVerified`, `Signals`, `Decision`, `ApproverId`, and `Attestations` from a request body have no effect
on either endpoint. Both go through one sanitizing step before the planner or the executor sees them.

### R2 — Verified evidence is derived, not accepted

Verified evidence comes only from a server-owned inventory resolved for the authenticated owner and the exact selected source folder. Files in sibling folders cannot satisfy the selected scope. Each
derived item carries a server-owned identifier (`SRC-<kind>`) and a server-owned source string, so a
report cannot be made to cite an operator's text as though the indexer produced it.

A caller's own declarations survive as declarations: same kind, `IsVerified = false`, no signals, a
server-authored summary. An operator saying a regression baseline exists is useful context; it is not the
same statement as the server having seen one.

### R3 — Deterministic source identity

Every acquired workspace gets a SHA-256 snapshot hash over sorted relative paths plus each file's length
and bytes. `.fleet-run` is excluded, because a run writing its own output must not change the identity of
what it read. Enumeration is bounded by the intake limits acquisition already applies, and a tree that
exceeds them hashes to a sentinel that matches no grant.

The hash is server-only. It is absent from `SourceWorkspaceSummary`, which is serialized to the browser,
and is reachable only through `SourceWorkspaceService.Describe`, which returns null to a non-owner.

### R4 — Authorization is a server-issued, fully bound record

A typed record binds a grant to: the authenticated actor, a required role, the engagement, the source
snapshot hash, the plan input hash, the target hash, one mutation scope, and an expiry. A store returns
grants for an owner and nothing in the request path may create one.

### R5 — Revalidation immediately before the side effect

`MigrationExecutor` consults an optional `IPhaseMutationAuthorizer` immediately before invoking any phase
whose `Mutation` is `SandboxDatabaseWrite` or `ProductionWrite`. A denial fails that phase, writes
nothing, and attests nothing.

The parameter is optional so existing in-process callers keep the contract they have. The Workbench API
always supplies one, and supplies one that fails closed.

### R6 — The default deployment authorizes no mutation

`NoWorkbenchAuthorizationStore` returns nothing, because there is nothing trustworthy to return. The
default API path therefore refuses every sandbox and production write. Planning and artifact generation
are unaffected: they write only inside the caller's own session workspace.

No approval is ever synthesized to compensate. Production additionally stays blocked because client
attestations are dropped and no server-owned attestation source exists.

### R7 — Every drift denies

Cross-owner, cross-engagement, changed source, changed plan input, changed target, wrong scope, missing
role, and expired grant each deny.

### R8 — Identity from the host boundary only

The owner comes from `X-MS-CLIENT-PRINCIPAL-ID`. Roles, when read, are parsed from the base64
`X-MS-CLIENT-PRINCIPAL` claim set the platform writes. No request JSON property is consulted for either.
An unparseable principal header yields no roles, so it denies rather than defaulting.

Authentication headers are honored only when `WORKBENCH_ENTRA_AUTH_ENABLED=true`; otherwise the actor is
`local-development` with no roles. The deployment must also ensure its authenticated ingress overwrites
those headers before a real authorization store is registered. Local development can plan and generate
and cannot mutate.

### R9 — The plan endpoint can see the source

The wizard sends `workspaceId` alongside the run request when a copied source exists, so the plan endpoint
can derive source facts the same way the execute endpoint does. With a manual source or no workspace, all
evidence is unverified — which is the truthful plan, not a degraded one.

A supplied workspace identifier that the actor does not own is rejected rather than silently treated as a manual source.

## Acceptance

A request that forges verification, signals, approvals, and attestations against an owned source:

- plans, and the plan reports the blockers the real evidence implies;
- generates artifacts, if the derived evidence clears a phase's own requirements;
- never reaches `SandboxMigration` or `ProductionCutover`;
- and, were the planner to authorize a mutating phase by some other route, is refused by the authorizer
  at the moment the adapter would have run.

## Known limits

- HTTP tests cover forged planning/execution and cross-owner workspace rejection on the real local host.
  Production ingress header overwrite behavior still requires deployment qualification.
- **No grant can be issued.** By design, until a trusted store exists.
- **Snapshot hashing reads every acquired file once at acquisition.** Bounded by the existing 60,000-file
  and 512 MB intake limits.
